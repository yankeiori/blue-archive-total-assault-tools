# スキル順探索: 遅延束縛による初期配置の列挙

`app/backend/skill_order.py` は「使いたいスキル順(手順)を実現する**開始スキル設定**
(初期配置)をすべて挙げよ」という問題を解く。素朴には初期配置の全順列を回して前向きに
シミュレートすればよいが、制約解除決戦(カード10枚)では $10! = 3{,}628{,}800$ 通りとなり
実用に耐えない。本書は、これを**カードの正体を必要になるまで決めない探索(遅延束縛)**に
置き換えた設計と、その正しさ・計算量をまとめる。

利用者向けの操作説明は `docs/manual.md` の「スキル順探索」節、TL テキストの読み取りは
`app/backend/tl_parse.py`(本書 §9)を参照。

## 1. ゲームのモデル

### 1.1 状態

カードは全 $n$ 枚。**初期配置**は $n$ 枚の並び $\ell = (\ell_0,\dots,\ell_{n-1})$ で、
先頭 $h$ 枚が手札(スロット $1..h$)、残りが山札(上から順)になる。

| モード | $n$ | $h$ |
|---|---|---|
| 通常戦 | 1〜6 | 3 |
| 制約解除決戦 | 1〜10 | 5 |

状態は (手札 $H$, 山札 $D$) の対。$H$ は長さ $h$ のリスト、$D$ はキュー(先頭が山札の上)。
カードの表現は次の4種類:

| 表現 | 意味 |
|---|---|
| `("N", i)` | 通常カード(スキル $i$) |
| `("C", a, b)` | コピーカード。複製キャラ $a$ のカードが $b$ のコピーに化けた状態 |
| `("P", p)` | **未確定カード**。初期配置の位置 $p$ にあるが、正体はまだ決めていない(§4) |
| `None` | 空欄スロット |

$n < h$ のときは手札の左から $n$ 枚だけが埋まり、残りは空欄で始まる。

### 1.2 遷移

手順の1ステップは `Step`(スキル・スロット指定・ドローフラグ・複製対象・撤退フラグ)で表す。
状態遷移は `_use` / `_retreat` に実装されている。

**(a) 通常の使用** — スロット $i$ のカードを使うと、そのカードは山札の**底**へ行き、
山札の**上**の1枚がスロット $i$ にドローされる。

$$H_i \to \text{pop}(D),\qquad D \to D \cdot H_i$$

順序が重要で、「底へ置いてから上を引く」ため、山札が空でもカードは即座に手札へ戻る
(カード2枚でも連打できる)。山札が空になるのは撤退か $n<h$ のときだけで、そのときは
$H_i \to$ `None` となり、**空欄スロットは以後補充されない**。

**(b) 複製(変化)** — 複製キャラ $a$ の元カードを対象 $b$ 指定で使うと、その場で
`("N",a) → ("C",a,b)` に化ける。**山札は動かず、ドローも起きない**(`action="transform"`)。

**(c) コピーの使用** — `("C",a,b)` を使うと、カードは $a$ に戻って山札の底へ行く
(`D → D·("N",a)`)。通常の使用と同じくドローが起きる。

**(d) ドローフラグ** — そのステップでスキルカードのドローが発生する場合に立てる。
使用カードが山札の底へ移った後、「**使用したスキルの元カード**」が山札にあれば、
山札の途中からでもそれを引き抜いて元のスロットへ入れる。無ければ通常どおり山札の上を引く。

- 通常カード $A$ なら、$A$ 自身が直前に底へ落ちているので必ず手札へ戻る(連打が可能)。
- コピー `("C",a,b)` なら「元カード」は $b$ の**通常カード**。$b$ が山札にあれば引き抜く。

**(e) 撤退** — 指定キャラのカードを場(手札・山札)から**完全に除外**する。手札にあった
場合はそのスロットへ山札の上を1枚ドローする(山札が空なら空欄)。カードの持ち主は
`("N",i)` でも `("C",i,b)` でも先頭の添字 $i$ なので、**複製キャラが撤退すればその場に
出ているコピーカードも一緒に消える**。撤退はカード使用ではないので、スロット指定と
ドローフラグは無視される。

## 2. 問題の定式化

決定変数は初期配置 $\ell \in \mathfrak{S}_n$(位置 $\to$ スキルの全単射)。
手順 $P = (s_1,\dots,s_m)$ が与えられたとき、

> $\ell$ から始めて $P$ を先頭から順に実行できるような、各ステップの**使用スロット列**
> $(c_1,\dots,c_m)$ が存在するか

を問う。ステップにスロット指定があれば $c_k$ は固定、なければ $1..h$ から選ぶ。
さらに手順間の制約(`same_slot` / `different_slots`)を満たす必要がある。

出力は $(\ell, \text{trace})$ の組の列挙で、trace は
`(使用スロット, 使用カード, action, step)` の列である(`action` は
`"use"` / `"transform"` / `"retreat"`、撤退が山札から起きた場合スロットは 0)。

## 3. 素朴な解法とその限界

全順列 $\ell$ を回して深さ優先でスロットを選ぶ方式は、旧実装そのものである。
計測(10枚/手札5、旧実装):

| ケース | 初期配置の列挙数 | 時間 |
|---|---|---|
| 6枚/手札3・手順12 | 720 | 0.00 s |
| 10枚/手札5・手順4 | 3,628,800 | **6.60 s** |
| 10枚/手札5・手順14 | 3,628,800 | **10.71 s** |

問題は2つある。

1. **手順が短いほど遅い**。枝刈りが効かず、$10!$ 個すべてを立ち上げる固定費が支配的になる。
2. **解が水増しされる**。手順に登場しないカードの並べ替えが全部別解として数えられ、
   手順4のケースで解が 450,000 件になる。人間が読める出力ではない。

どちらも「使わないカードの順列」を明示的に展開していることが原因である。

## 4. 遅延束縛 DFS

### 4.1 未確定カード

初期配置を先に決める代わりに、全カードを未確定カード `("P", p)` として置く。
$p$ は初期配置の**位置**で、手札に $("P",0),\dots,("P",h-1)$、山札に $("P",h),\dots$ が並ぶ。

探索の状態に次を持ち回る。

| 変数 | 意味 |
|---|---|
| `assign` | 位置 $\to$ スキル の部分写像(確定済み) |
| `used` | 確定済みスキルの集合(= `assign` の像) |
| `nocop` | 「複製キャラであってはならない」位置の集合(§4.3) |

手順がカードを要求した時点で初めて $p := s$ と確定させる。手順に一度も現れないカードは
最後まで未確定のまま残り、その並べ替えは**展開せずに通り数として数え上げる**(§4.4)。

### 4.2 束縛規則(`_dfs`)

スロット $i$ のカードに対する判定は次のとおり。分岐(=探索木の枝)は
**スロットの選択でのみ**起き、束縛そのものは1通りに定まることが要点である。

| カード | ステップ | 判定 |
|---|---|---|
| `("P",p)` | スキル $s$ 指定 | $s \in$ `used` なら**不一致**(すでに別の位置にいる)。そうでなければ $p := s$ と確定して使用 |
| `("P",p)` | ワイルドカード | 束縛せずに使用。ただし複製キャラがいる編成では $p$ を `nocop` に追加 |
| `("P",p)` | コピー使用 | 不成立(コピーカードは未確定にならない) |
| 確定カード | 各種 | 従来どおりカードとステップを直接照合 |

「$s$ が既に別の位置に確定しているなら、いま目の前の未確定カードは $s$ ではありえない」
という枝刈りが効くため、手順が長いほど木は細くなる。

### 4.3 ワイルドカードと `nocop`

ワイルドカード(「指定なし」)は**複製キャラの元カードを使わない**(複製対象を決められない
ため)。未確定カードをワイルドカードで使う場合、正体を決めずに「この位置は複製キャラでは
ない」という制約 $p \in$ `nocop` だけを積む。制約が一様なクラス(「複製キャラ禁止」)なので、
最後の数え上げ(§4.4)を閉じた式のまま保てる。

同時に、**残りの複製キャラを置ける自由位置が足りているか**を見て枝刈りする
(`room < 残りの複製キャラ数` なら不成立)。

### 4.4 自由位置の数え上げ(`_record`)

全手順を消化したら、未確定のまま残った位置 $F$(自由位置)に、未使用スキル $R$(同数)を
割り当てる方法の数を数える。$K = |\{$複製キャラ$\} \cap R|$、
$U = |F \setminus \texttt{nocop}|$ とすると、複製キャラは `nocop` の位置に置けないので

$$\#\{\text{割り当て}\} = \underbrace{P(U,K)}_{\text{複製キャラを制約なし位置へ}} \times \underbrace{(|F|-K)!}_{\text{残りは自由}}$$

これが `Solution.count` である($P(U,K)=U(U-1)\cdots(U-K+1)$、`_perm`)。
複製キャラがいない編成では単に $|F|!$ になる。具体的な配置が必要なときは
`Solution.expand()` が `nocop` を守りつつ列挙する。

### 4.5 唯一の分岐点(`_locate`)

「あるスキル $b$ のカードが**いま山札にいるか**」を知る必要がある操作が2つある。

- **ドローフラグ**付きのコピー使用(元カード $b$ を山札から引き抜けるか)
- **撤退**(撤退するカードが手札にあるか山札にあるか)

$b$ が未確定の場合、答えは「どの未確定位置が $b$ だったか」に依存する。そこで `_locate` が
**生きている未確定位置それぞれに $b$ を束縛して分岐**する。$b$ が確定済みならカードの
居場所は一意なので分岐は起きない。この扇形の広がりは上記2操作でのみ発生し、
実測でも支配的にはならなかった(§5)。

なお `_use` は「使ったカードを山札の底へ置き、`H_i` を `None` にしてから」`_locate` を
呼ぶ。こうしないと、使用中のカード自身が未確定のとき、手札と山札の両方に同じ
プレースホルダが見えて二重に束縛されてしまう(実装初期に踏んだ)。

### 4.6 打ち切りと診断

- `max_results`: 解がこの数に達したら `_StopSearch` で脱出し、`truncated=True` を返す。
  探索時間はこの値にほぼ比例する(下表)一方、**表示に使われるのは先頭の表示件数分だけ**で、
  DFS は同じ順に解を積むので上限を下げても表示内容は1件も変わらない。そこで UI は
  `max(表示件数上限, 500)` を渡す。下限 500 は「実際に絞り込めている手順なら正確な件数が
  出る」ようにするため(枠を5つ固定した 98 手 TL は 120 件、6枚モードの TL は 162 件)。

  98手TL・最終手を1番目に固定した場合の実測:

  | max_results | 50 | 200 | 1,000 | 5,000 | 20,000 |
  |---|---|---|---|---|---|
  | 探索時間 | 0.02 s | 0.09 s | 0.45 s | 2.44 s | 9.79 s |
  | 表示される先頭の解 | ← すべて同一 → | | | | |
- `node_budget`: **無駄な探索**に許すノード数の上限。超えたら `SearchBudgetExceeded`。
  ワイルドカードを並べすぎた場合の保険である。2つの補正を入れている。
  - 既定値は `default_node_budget(plan) = max(2,000,000, 200,000 × 手順長)`。
    絶対値で固定すると、長い TL(実測 98 手)が**正当な探索なのに打ち切られる**。
  - 解を `max_results` 件そろえるには最低でも `max_results × 手順長` ノードを辿る
    必要があるので、その分は上限とは別枠で加算する。
  - 明示的に渡した `node_budget` はそのまま尊重する(保険としてのテストが書ける)。
- `stats`: dict を渡すと `stats["max_depth"]` に**探索が到達できた最大の手順数**が入る。
  解が0件のとき「何手目で成立しなくなるか」がこれで分かる。`max_depth == 手順長` なら
  手順自体は最後まで通っており、落としたのは手順間の制約である。UI はこれを使って
  「◯手目までは成立し、△手目「XXX」で成立しなくなります」と表示する。

`max_depth` は `_dfs` の入口で `i` の最大値を記録するだけなので**追加コストがない**。
当初は「成立する最長の前半を二分探索する」実装にしたが、長い前半の不成立を証明するのに
毎回木を尽くす必要があり、実測 92 秒かかったうえ予算超過で位置がずれた。

## 5. 計算量と実測

初期配置のループが消えたので、コストは**解の個数**にほぼ比例するようになった。
現行実装での計測(`node_budget` 無制限):

| ケース | 解(圧縮) | 時間 |
|---|---|---|
| 6枚/手札3・手順12 | 162 | 0.00 s |
| 10枚/手札5・手順4 | 625 | 0.18 s |
| 10枚/手札5・手順14 | 375,000 | 4.63 s |
| 10枚/手札5・手順18 | 375,000 | 6.47 s |
| 10枚/手札5・手順18(枠を5つ固定) | 120 | 0.08 s |
| 10枚/手札5・複製+ドロー8手 | 46,080 | 0.31 s |
| 7枚/手札5・手順6 | 3,000 | 0.02 s |

手順4は 6.60 s → 0.18 s、しかも解は 450,000 件 → 625 件に圧縮された。

残る重いケース(手順14/18で枠指定なし)は探索の無駄ではなく、**解が本当に 375,000 個ある**
ことによる。実際 $375{,}000 = 5^5 \times 5!$ で、これは「最初の5手はどの手札枠を使っても
よい」自由度と、手札5枚の並べ替えの積である。枠を1つでも固定すれば上表のとおり即座に
終わる。UI は `max_results=20000` で打ち切るため、同じ手順18でも **0.20 s** で返る。

将来の改善余地として、未確定カードが入っている手札枠は互いに対称なので、代表1枠だけ
探索して倍率を掛ける**対称性圧縮**が考えられる。ただし枠固定ステップがあると対称性が
壊れるため、「枠指定が1つも無い場合のみ」という条件付きになる。現状は未実装。

### 実例: 98手の制約解除決戦 TL

`tl_sample/貫通コクマー_123用調整.txt` を読み込んだ 98 手(10枚/手札5、複製=リオ)での実測。

| 条件 | 解 | 初期配置 | 時間 |
|---|---|---|---|
| 枠指定なし・全列挙 | 300,000 | 200,000 以上 | 39.5 s |
| 最終手を「1番目」に固定・全列挙 | 60,000 | 60,000 | 27.8 s |
| 最終手を「1番目」に固定・UI(表示60件 → 上限500) | 500+ | — | **0.27 s** |

98 手あっても初期配置は 60,000 通り残り、手札5枚の組合せだけで 111 通りある。
**長い TL でも初期配置はほとんど絞れない**(TL はカードの並びではなく使用順しか
指定しないため)。絞るには枠指定や手順間の制約を足す必要がある。

## 6. 解の数え方

2種類の数が混ざるので注意する。

- `len(results)` — **解(trace)の数**。同じ初期配置でも使用スロットの選び方が違えば別解。
- `distinct_layouts(results)` — **初期配置の種類数**。展開して集合に入れて数える。
  既定 `cap=200000` を超えたら `(cap, False)` を返す(「これ以上ある」の意)。
- `total_layouts(results)` — `count` の総和。**同じ初期配置を trace の数だけ重複計上する**。

手順が完全に指定されている(ワイルドカードが無い)場合、初期配置 $\to$ trace は関数に
なるので両者は一致する。ワイルドカードがあると一致しない。例:
6枚で手順「指定なし・指定なし」の場合、`total_layouts` は 6,480 だが実際の初期配置は
$6! = 720$ 通りしかない。UI は `distinct_layouts` を表示する。

## 7. 正しさの検証

`tests/test_skill_order.py` に**参照実装** `_ref_solve` を同梱している。これは §1 の
遷移をそのまま素直に書いた、初期配置を全列挙する遅い実装である。テストは

- 遅延束縛版の各解を `expand()` で具体化し、`(初期配置, 使用スロット列)` の**多重集合**が
  参照実装の出力と一致すること
- `Solution.count` が `expand()` の個数と一致すること

を、複製・コピー・ドロー・撤退・枠固定・ワイルドカード・空スロット・手札5枚を混ぜた
**固定15ケース**と、乱数生成した**120ケース**で確認する。この突き合わせで実装初期の
取りこぼしを2件検出した(§4.5 の二重束縛と、`nocop` による過剰な枝刈り)。

## 8. 実装対応表

| 概念 | 実装 |
|---|---|
| 手順1ステップ | `Step`(`skill` / `use_copy` / `copy_target` / `slot` / `draw` / `retreat`) |
| 探索本体 | `solve` → `_dfs` |
| 使用の状態遷移 | `_use` |
| 撤退の状態遷移 | `_retreat` |
| カードの居場所の確定(分岐点) | `_locate` |
| 解の登録と自由位置の数え上げ | `_record`、`_perm` |
| 解 | `Solution`(`layout` / `trace` / `count` / `free` / `nocopier`、`expand()`) |
| 手順間の制約 | `same_slot`、`different_slots` |
| 表示 | `slot_labels`、`card_label`、`trace_entry_label` |
| 打ち切り | `SearchBudgetExceeded`、`_StopSearch` |

`layout` の要素が `None` の位置は「残りのどのカードでもよい」を意味し、UI では「任意」と
表示される。

## 9. 付録: TL テキストの読み取り

`app/backend/tl_parse.py` は総力戦の TL テキストを手順に変換する。探索ロジックとは独立だが、
テキストからは一意に決まらない点を**推定 + 警告**で埋めているので、その方針を記しておく。

- 発動タイミングの注記(`即` `オート` `11` `10.5` `3:03.000` `◯◯NS後` `コストカット後` …)、
  `/` `//` `※` `【` 以降、`目標…` の行、`〆` は読み飛ばす。
- `cマリー` `Cマリー` `マリー(コピー)` はコピー使用。`リオ(マリー)` は複製キャラなら複製対象、
  そうでなければ対象注記としてメモへ。`◯◯撤退` は撤退。名前が連結していても分割する。
- **複製対象の省略**(`即 リオ` とだけ書かれている): 後続の `c◯◯` から対象を推定し、警告を出す。
- **同じカードの連続使用**: §1.2(a) より、ドロー無しでは絶対に成立しない。よって直前の手に
  ドローフラグを立て、警告を出す。ただし実際には「2つ目が `c` 省略のコピー使用」である
  可能性もあるため、警告文でその旨を併記する(サンプル TL に実例があり、16通りの解釈を
  総当りしたところコピー解釈だけが成立した)。
- カード名は `ドアル/アル` のように `/` 区切りで別名を書ける(先頭が表示名)。TL の略称ゆれ用。

推定はあくまで補助なので、**解が0件になったときはまずこれらの警告を疑う**のが早い。
